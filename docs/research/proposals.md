# 提案（役割①の出力）

毎時、役割①がユーザー満足・収益・信用の観点で 1 件書く。新しいものを上に。
役割②はここの最新を読んで設計する。標準制約（対外発信しない・金額/契約を
決めない・経営ゲートの数値を変えない・main へ push しない）に触れる提案は
**要判断** と明記し、人が決めるまで役割②以降に流さない。

書式:

## <日時> <提案名>
- 状態: 未設計 / 設計済み / 実装済み / 要判断
- 何を: / なぜ: / 期待効果: / 根拠の事例: case-studies.md の番号

---

## 2026-08-08 21:20 JST 月次経営レコードの受け皿（docs/finance/monthly-record.md）
- 状態: 設計済み（designs.md 2026-08-08 21:25）
- 何を: 月ごとに「収入・支出・KPI 実績」を**事実だけ**記録する台帳の型を
  `docs/finance/monthly-record.md` に作り、2026-08 分の初回レコードを
  書き始める。収支がゼロの月は**ゼロと記録する**。KPI は docs/KPI.md の
  指標と同じ並びにし、計測できていないものは「未計測」と書く（数字を
  作らない）。金額・価格の**決定はしない**（記録のみ＝標準制約の範囲内）。
- なぜ: KPI.md に指標と目標はあるが、実績を毎月同じ形で記録する器が無い。
  Buffer は 2013 年から月次の定型レポートで財務公開を続け（事例 3）、
  Ghost は数字のライブ公開を信用の土台にしている（事例 4）。どちらも
  「続けられる定型の器」が先にある。gdp・役割④が数字で議論するにも器が要る。
- 期待効果: 経営ゲート（README）の達成判定が毎月同じ場所でできる（経営企画）。
  将来「公開する/スポンサーに見せる」を人が選べる状態を作る（信用）。
  未計測の指標が明示され、site 側の計測実装の優先順位づけに使える（収益）。
- 根拠の事例: case-studies.md の 3・4
- 状態: 実装済み（docs/pr/press-kit.md, 483c25b）
- 何を: GAMEYARD のプレスキット下書きを `docs/pr/press-kit.md` として作る。
  節は presskit() の標準構造に合わせる（概要 / 事実シート: 開発元・公開状況・
  URL・価格 / 特徴 / 画像・ロゴの置き場所 / 連絡先）。事実は site リポジトリ
  （README・SPEC）から取り、出典の無い数字・実績は書かない。
  **対外公開・配信はしない**（下書きまで。公開は人が決める＝標準制約の範囲内）。
- なぜ: 全社戦略の最優先はユーザー・投稿作品の獲得（8 月第 2 週）で、
  第 3 週にスポンサー営業開始の目安。紹介・取材・営業のどの経路でも
  「まとまった事実資料」が最初に要る。業界では無料ツールで整うのが標準
  （事例 1・2）で、無い状態は機会損失。
- 期待効果: 掲載・紹介への即応（ユーザー満足＝知って遊びに来る人が増える）。
  スポンサー提案書の土台になり営業開始が速くなる（収益）。事実が 1 か所に
  固定され、対外説明のブレが消える（信用）。
- 根拠の事例: case-studies.md の 1・2
