# 自動で作り続けるときの決まり（コーポレート部門）

SIDRA STUDIO のコーポレート部門（広報戦略・経理・経営企画などの統括）を
無人で回すための作業規則。構造は GAMEYARD
（[tukemen-rgb/site の docs/autonomous-loop.md](https://github.com/tukemen-rgb/site/blob/main/docs/autonomous-loop.md)）
と同じ。**判断に迷ったら止まって聞く**のではなく、**判断に迷うことを
そもそも作業に含めない**（迷う類のものは人が決める）。

## このリポジトリの担当

経営判断の一元管理。成果物はコードではなく**文書**（戦略・広報・経理・
経営企画）。事業リポジトリの実態は参照して使う:

- [tukemen-rgb/site](https://github.com/tukemen-rgb/site) — GAMEYARD 本体
- [tukemen-rgb/creater-yard](https://github.com/tukemen-rgb/creater-yard) — CreatorYard
- [tukemen-rgb/marketing](https://github.com/tukemen-rgb/marketing) — マーケティング

参照は読み取りのみ。**他リポジトリへの push はしない。**

## 分担

| | 間隔 | 担当 |
| --- | --- | --- |
| **gdp（ChatGPT）** | お題は 2 時間で 1 つ。連携コメントは毎時 :00 | 経営視点のレビュー・優先順位・指摘 |
| **Claude Code**（ここ） | 2 時間で 5 役（20 分間隔） | 調査・設計・実装・監査・調停 |

### 往復は AI Review Board（[Issue #1](https://github.com/tukemen-rgb/Fg/issues/1)）でやる

人にテキストを持ち運ばせない。やりとりはすべて Issue #1 のコメントに書く。

- **読む** … `mcp__github__issue_read`（`method: get`）で**コメント総数だけ**
  先に見る。前回より**増えたときだけ**、`get_comments` の最後のページを読む。
  総数が同じなら読まない（トークンを使わない）
- **gdp は 1 サイクル（2 時間）の途中でも書き込む。** お題は 2 時間で 1 つ
  だが、連携コメントは 1 時間に 1 回入る（**JST 奇数時 :00** のお題、
  **JST 偶数時 :00** の連携）。**5 役はどれも毎回コメント総数を確認する**。
  とくに④（**JST 偶数時 :10**）は直前の **JST 偶数時 :00** の連携を拾う
  位置にいるので、増えていれば必ず読んでレポートに反映する
- **書く** … `mcp__github__add_issue_comment`。役割④のレポートと
  役割⑤の裁定だけが書く。**変化が無い周の重複レポートは投稿しない**

判断を仰ぎたいことは、レポートの末尾に**質問として明記する**。勝手に決めない。

## 5 役ローテーション（20 分間隔・2 時間で 1 サイクル）

予約は Routine 5 本。**cron は UTC で評価される**ため、下表は JST・UTC・cron を
併記する（恒常規則「時刻は時間帯つきで書く」）。1 役割の持ち時間は **20 分**。
gdp（ChatGPT）は **JST の奇数時 :00 にお題**を出し、**JST の偶数時 :00 に連携**を書く。

| 役割 | JST | UTC | cron | 出力先 |
| --- | --- | --- | --- | --- |
| gdp（ChatGPT）— その 2 時間のお題 | 奇数時 :00 | 偶数時 :00 | （人が実行） | Issue #1 |
| ① 調査・提案（gdp の意見＋他社事例。**gdp の意見が無い/承認待ちで止まっているときは、これまでの GitHub の内容から Claude が自分で論点を立てて提案する**） | 奇数時 :10 | 偶数時 :10 | `10 0-23/2 * * *` | docs/research/case-studies.md, proposals.md |
| ② 技術設計（**リスク節を必須にする**: 財務・法務・信用/ブランド） | 奇数時 :30 | 偶数時 :30 | `30 0-23/2 * * *` | docs/research/designs.md |
| ③ 実装（設計を文書・仕組みに落として commit） | 奇数時 :50 | 偶数時 :50 | `50 0-23/2 * * *` | 成果物＋designs.md に実装済み印 |
| gdp（ChatGPT）— サイクル途中の連携 | 偶数時 :00 | 奇数時 :00 | （人が実行） | Issue #1 |
| ④ 監査・報告（①〜③の一貫性と既存文書との整合→docs/cycle-report.md→Issue #1） | 偶数時 :10 | 奇数時 :10 | `10 1-23/2 * * *` | docs/cycle-report.md, Issue #1 |
| ⑤ 調停（gdp と Claude の意見のズレを、ユーザー満足・収益・信用の中立で裁いて①〜④へ次の指示を出す） | 偶数時 :30 | 奇数時 :30 | `30 1-23/2 * * *` | docs/research/mediation.md, Issue #1 |

④の「この周の変化」は**前回の④レポート以降**を指す（1 時間ではなく 2 時間分）。

### 回し方の決まり

- **前の役割の処理がまだ走っていたら、重ねずに見送る**
- **20 分に収まらない処理は background で回し、次の役割は見送りにする。
  切り上げない**（半端な成果物を残すより 1 枠飛ばすほうが安い）
- **変化なしの周は確認だけでスキップする。** この運用はトークン消費が
  大きい。2 時間 1 サイクルにして 1 時間 5 役だった頃の半分になったが、
  それでも 90 分 1 本と比べれば数倍あるので、この規則が効いてくる。
  スキップした周は commit もコメントもしない
- 事例は**累積 100 件以上が目標**。1 周で埋めるために推測を書かない

### 恒常規則（⑤の裁定で追加。緩和はしない）

| 規則 | 内容 | 解除条件 | 出典 |
| --- | --- | --- | --- |

| 変化なし周のスキップ | 新しい事実（gdp・人の回答・他リポジトリの変化）が無い周は確認だけで終了してよい | なし（常時） | mediation.md 2026-08-09 00:50 |
| 1 周を軽くする | ①は事例 1〜2 件・提案 1 件・裏取り URL 2 件までに抑える。②③は既存ファイルの磨き込みを優先 | なし（常時） | mediation.md 2026-08-09 06:32 |
| 出典が無い周は点検にあてる | 事例の出典が取れない周は、手持ちの文書の点検にあてる（放置でも推測でもなく、点検 → 穴が有れば提案・無ければその旨を残す） | なし（常時） | mediation.md 2026-08-09 18:50 |
| 時刻は時間帯つきで書く | 予約・発火・締切など**時刻を書くときは必ず時間帯を添える**。cron は UTC で評価されるため、cron 由来の時刻は **JST と UTC の両方**を書く | なし（常時） | mediation.md 2026-08-09 22:35 |
| 検査は設計の転記先に従う | ④が一貫性を機械照合するときは、**②の設計が指定した転記先**（どのブロックがどのファイル・どの Issue へ行くか）に対象を限る。設計に無い範囲を独自に掃かない。**不一致が出たら、まず検査の対象が正しいかを疑う**（誤検出は無い不整合を報告し、次の周を空回りさせる） | なし（常時） | mediation.md 2026-08-10 00:35 |

  （追加の経路は「⑤が裁定 → ①〜③が規則文書へ反映」に一本化する）

## 常に守るもの

| 決まり | 確かめ方 |
| --- | --- |
| 文書間の整合を壊さない | README・docs/STRATEGY.md・docs/ROADMAP_90D.md・docs/KPI.md と矛盾しないか読み合わせる |
| 事実と提案を分ける | 出典の無い数字・実績を書かない。推測は推測と明記 |
| commit は小さく | 1 つの commit で 1 つのこと。事例追記と提案は分けてよい |
| 作業ブランチのみ | `claude/autonomous-loop-setup-m7z9rg` に push。main へは出さない |

## 人が決めるまで変えない一覧（プロジェクト固有・育てる）

| 項目 | 理由 |
| --- | --- |
| 経営ゲートの数値（README / docs/KPI.md） | 投資判断の基準そのもの |
| 事業の順序と北極星指標 | 全社戦略の骨格 |
| **対外発信**（プレスリリース・SNS 投稿・営業メールの送信） | 出したら取り消せない。文面の**下書きまで**は作業してよい |
| **第三者に依頼する広報**（インフルエンサー・レビュアー・記事広告などへの依頼） | 日本のステマ規制では**表示の責任は広告主となる事業者**にあり、依頼した SIDRA 側が負う（消費者庁・2023-10-01 施行。docs/research/case-studies.md の 15）。個別の適法性は人（必要なら専門家）が判断する |
| 金額・契約・支払い・価格の決定 | 経営の判断であって文書の判断ではない |
| main への push・PR の merge | 人が決める。**2026-08-09、社長が「いい感じでやっておいて」と反映のタイミングを委任**。作業ブランチで①〜⑤を回し、区切りのついた分だけ main へ早送りする（内容の判断を委ねられたわけではない。要判断の項目はこの表の他の行のまま） |
| 他リポジトリへの push | このループの権限外。参照のみ |

判断が必要になったら、その項目に**要判断**と明記して人が決めるまで
役割②以降に流さない。設計の判断そのものは gdp 側の担当なので、
迷ったものは「gdp からの指摘」を待つ形にしてよい。

## 環境メモ（プロジェクト固有）

**このリポジトリで実際に踏んだものだけ書く。** 他プロジェクトのメモ
（site の clamd・pgrep・Playwright 等）をそのまま持ち込まない。

- 2026-08-08: docs のみのリポジトリ。package.json・試験・ビルドは無い。
  「確認」は文書整合の読み合わせを指す
- 2026-08-08: 他リポジトリの参照は匿名 git clone で読む
  （`GIT_LFS_SKIP_SMUDGE=1 git clone --depth 1`）。GitHub API はこのリポジトリの分しか使えない
- 2026-08-08: 予約は Routine 5 本（このセッションに発火）。:30 の予約は
  サーバー側の混雑回避で数分後ろ（:32〜:34 前後）にずれて発火する。
  持ち時間 20 分のうちに収まるので許容（2026-08-09 の 2 時間サイクル化後も
  ②＝**JST 奇数時 :30**・⑤＝**JST 偶数時 :30** で同じずれを確認）
- 2026-08-09: 番号を grep で数えると**部分一致する**（"15" が "5" に
  一致）。事例の索引など番号つき一覧を照合するときは、区切りを含めた形
  （`^## 5\. ` や `・5（`）で数える。第 12 周に④が踏んだ

## 記録

- `docs/research/` — 受け皿 4 ファイル（case-studies / proposals / designs / mediation）
- `docs/cycle-report.md` — 役割④が毎周追記（初回に作成）

**何に気づいたか・何を避けたか**を残すほうが役に立つ。
